# Legalwork 知识库架构改良报告

> 日期：2026-07-31
> 范围：基于一次关于「RAG vs Agentic Search」技术路线讨论引发的对 legalwork 现有知识库架构的审视与改良方案

---

## 一、对话背景

### 1.1 起因

一次微信评论区关于 AI 检索技术路线的讨论中，出现了两种对立观点：

- **观点 A**：RAG（检索增强生成）已是强弩之末，真正实用的技术还得是 Agentic Search。
- **观点 B**：正确方向是 **Agentic Search + LLM wiki + 向量化** 三者结合。

这条讨论引发了对 legalwork 现有知识库架构的审视：legalwork 目前的知识库到底属于哪一条路线？在当前规模下够不够用？如果知识库扩大到上万文件，还能不能扛住？

### 1.2 本次讨论的核心问题

1. legalwork 现在的知识库建构属于哪种技术路线？
2. 如果知识库文件规模扩大到 1 万+，哪种方案效果最好？

---

## 二、Legalwork 现有知识库架构盘点

通过对代码的完整梳理，legalwork 现有架构总结如下：

### 2.1 整体架构：文件系统稀疏检索 + Agentic 编排

Legalwork 采用**两层混合架构**，而非传统向量 RAG：

- **第一层 · 本地知识库**：基于文件系统的稀疏检索系统，**不使用任何 embedding 模型，也没有向量数据库**。
- **第二层 · Agentic 编排层**：`CaseAIOrchestrator`（Python）与 `KnowledgeRetrievalPipeline`（TypeScript）充当智能编排层，负责查询拆解、分层路由、来源合并、有效性过滤、外部法律库回退。

### 2.2 知识内容形态（wiki 结构）

知识库本体是人工撰写的结构化 Markdown 文档（约 163 篇），配 `.meta.json` 元数据侧边文件，组织为：

- 经验分享/法律调研
- 经验分享/日常基本工作方法
- 经验分享/案件准备
- 经验分享/新人入门篇
- 经验分享/价值观及律师执业理念
- 经验分享/团队管理
- 经验分享/成长及进步
- 经验分享/时间管理

这一层**天然就是「wiki + 结构化知识」的形态**——知识是可读、可维护、带版本和置信度标记的，而不是一堆无意义的切片碎片。

### 2.3 检索实现（当前短板所在）

**召回完全靠稀疏 TF 向量（词频余弦相似度）：**

```python
def vectorize(text: str) -> dict[str, float]:
    counts = Counter(tokenize(text))
    norm = sqrt(sum(v*v for v in counts.values())) or 1.0
    return {k: v / norm for k, v in counts.items()}

def cosine(a, b) -> float:
    return sum(v * b.get(k, 0.0) for k, v in a.items())
```

- 中文按**双字滑动窗口**切分（bigram），构建词频向量
- 每次查询**全量加载 chunks.json 到内存线性比对**（O(n)）
- TypeScript 端略好：有多因子打分（短语匹配 +12、层级加权 +8、词频 +1.2~2.4、字段命中 +5、关键词余弦 ×18、邻近度 +6）和 MMR 多样性重排，但**底层仍是稀疏词频检索**

### 2.4 Agentic 编排（现有优势所在）

- **Pyramid 分层路由**：查询先按 5 层知识金字塔（原则→架构→标准→实现→经验）路由，14 组规则集关键词匹配决定搜哪些层
- **多来源合并**：案件材料 + 案件知识 + 全局知识三方检索去重合并
- **有效性过滤**：读 `.meta.json` 的 `deprecated` / `expiresAt` 字段，过滤过期/失效内容
- **外部法律库回退**：本库命中不足时自动查询**国家法律法规数据库**（flk.npc.gov.cn）官方 API
- **引用溯源校验**：生成后逐条核对模型引用的原文是否真实存在于文档中（精确引用比对）

### 2.5 现有架构定位总结

| 维度 | 现状 |
|---|---|
| 召回方式 | 稀疏词频 + 规则路由 |
| 语义理解 | 无 embedding，纯关键词重合 |
| 多步推理 | 有（Plan Task 拆解 + 分层路由 + 外部 API 回退） |
| 引用验证 | 有（Source Verifier 精确引用比对） |
| 知识形态 | 结构化 wiki（.md）+ 侧边元数据 |
| 高性能索引 | ❌ 无，线性扫描 |

**一句话定位：legalwork 有 Agentic 编排的骨架 + wiki 结构化的底座，但缺「向量化」和「高性能索引」这两层。**

## 三、核心问题：大规模文件下的瓶颈

### 3.1 一万文件场景下的三个致命问题

**① 性能崩塌（最致命）**

现有实现是线性扫描：每次查询全量加载所有 chunk 到内存逐条算余弦相似度。

- 1 个文件 ≈ 20 个 chunk
- 1 万个文件 ≈ **20 万条逐条比对**
- 延迟从秒级直接劣化到分钟级，完全不可用

**② 无语义召回能力**

没有 embedding，「诉讼时效」和「权利行使期限」这类**语义等价但字面不同**的表达完全匹配不上。法律文书恰恰充斥着这类近义改写。

**③ 结构层级信息在检索层丢失**

知识库本体虽是结构化 wiki，但检索时切成 2400 字固定窗口后，第 X 条第 X 款的层级关系就丢了，无法做"精确锚定到某一条"的引用。

## 四、方案对比（一万文件规模）

### 方案 A：纯稀疏检索（legalwork 现状）
| 维度 | 评价 |
|---|---|
| 1 万文件性能 | ❌ 线性扫描 20 万+ 条比对 |
| 语义理解 | ❌ 无，近义改写匹配不上 |
| 法律术语精度 | ✅ 关键词对上即高准度 |
| 维护复杂度 | ✅ 极低，纯 JSON |
| **结论** | **不可行，必须换索引** |

### 方案 B：纯向量 RAG
| 维度 | 评价 |
|---|---|
| 1 万文件性能 | ✅ ANN 索引（HNSW/IVF）亚秒级 |
| 语义理解 | ✅ 近似语义可匹配 |
| 法律术语精度 | ⚠️ 普通 embedding 对「不可抗力」与「情势变更」的边界模糊 |
| 结构保持 | ❌ 切片后层级关系丢失 |
| 成本 | 1 万文件 embedding 费 + 向量库运维 |
| **结论** | **能跑，但对法律场景不够精准** |

### 方案 C：纯 Agentic Search
| 维度 | 评价 |
|---|---|
| 1 万文件性能 | ❌ 每次让 LLM 决策检索路径，延迟 ×3~10 |
| 多跳推理 | ✅ 复杂法律问题拆解能力强 |
| 成本 | ❌ 每问烧多次 LLM 调用，成本扛不住 |
| **结论** | **杀鸡用牛刀，不适合海量文档日常检索** |

### 方案 D：Agentic Search + wiki + 向量化（推荐方向）

这才是 1 万文件规模下法律知识库的最优解：

```
        查询
         │
         ▼
    ┌─────────┐
    │  Agent   │   ← 简单查询直走检索层；复杂问题才拆解编排
    └────┬────┘
         │
    ┌────┴────┬─────────┐
    ▼         ▼         ▼
 向量搜索    关键词搜索  结构锚定
 (语义粗召)  (精确匹配)  (wiki 层级定位)
 ANN<100ms   ES<50ms    ├─第X条→第X款
    └────┬────┘         └─引用源文件
         │
         ▼
    混合排序（RRF 融合）
         │
         ▼
   Agent 综合 + 引用溯源校验
```

| 维度 | 评价 |
|---|---|
| 1 万文件性能 | ✅ 向量库 ANN + ES 倒排，毫秒级 |
| 语义理解 | ✅ embedding 兜底近义召回 |
| 法律精度 | ✅ ES 精准匹配补上 embedding 的模糊 |
| 结构保持 | ✅ wiki 层存原始层级，引用可锚定到条 |
| 多跳推理 | ✅ Agent 按需编排 |
| 成本 | ✅ 可控——90% 查询只走检索层，无需 LLM |

## 五、改良思路（详细方案）

### 5.0 改良总原则

> **保留骨架，替换心脏。**
> 现有 Agentic 编排层（金字塔路由、多来源合并、有效性过滤、引用校验）是已验证的资产，全部保留。
> 替换的是检索底层：**去掉线性扫描，换成「向量库 + 倒排索引」双路召回 + RRF 融合。**

### 5.1 第一阶段：加向量化层（解决语义召回）

**目的**：补齐 embedding，让「诉讼时效」能召回「权利行使期限」。

| 项目 | 方案 |
|---|---|
| 向量模型 | 中文法律领域 embedding（如 `m3e-base` / `bge-large-zh` 或通义 `text-embedding-v3`） |
| 向量库 | 轻量优先：PGVector（直接复用现有 PostgreSQL）→ 规模再大换 Qdrant |
| 切片粒度 | 法律语义切片（保留现有 `SemanticChunker` 的第X条层级输出）而非固定窗口 |
| 召回 | ANN 粗召回 Top-K（K=50） |

**关键决策**：切片不推翻现有固定窗口，而是**双轨并存**——结构化文档走语义切片，非结构化文档保留滑动窗口。

### 5.2 第二阶段：加倒排索引（解决精确匹配与性能）

**目的**：把"按条款查、按法条号查、按案由查"这类精确检索从线性扫描中解放出来。

| 项目 | 方案 |
|---|---|
| 方案 | Elasticsearch（自托管）或 Meilisearch（更轻） |
| 索引字段 | 标题、正文、元数据（标签/案由/法条号）、路径、关键词 |
| 查询 | bool 查询：must（关键词）+ filter（有效性/层级过滤） |
| 高亮 | ES 自带高亮，直接支撑引用锚定 |

**ES 的存在意义**：embedding 擅长"模糊"，倒排索引擅长"精确"。法律场景两者缺一不可——法条号必须精确命中，语义扩展由向量补。

### 5.3 第三阶段：双路召回 + RRF 融合（解决精度与召回的平衡）

```
查询 → 并行发起
    ├─ 向量路：query embedding → ANN 召回 Top-50
    └─ 关键词路：query → ES 召回 Top-50
              ↓
        RRF 融合排序：
        score(d) = Σ 1/(k + rank(d))   （k=60）
              ↓
        过滤：有效性（deprecated/expiresAt）+ 层级过滤
              ↓
        重排：现有 MMR 多样性重排复用
              ↓
        注入 Agent 上下文（保持现有 8000 字上限）
```

**为什么用 RRF 而不是权重加权**：RRF 不看具体分数，只看排名位次，天然规避了向量分数与 ES 分数量纲不可比的问题，实现简单、效果稳。

### 5.4 第四阶段：Agent 编排层增强（复杂问题按需深度检索）

在现有 `KnowledgeRetrievalPipeline` 之上增强：

```
Agent 决策流程：
1. 查询进来 → 先走 5.3 双路召回（快路径，<200ms）
2. 若快路径置信度不足（召回太少/来源都是低置信度）：
   a. 将查询拆解为多个子查询（法条 + 案例 + 实务经验）
   b. 每个子查询独立走双路召回
   c. 对关键争议点，触发外部法律库检索（国家法律法规数据库）
3. 汇总 → 现有金字塔路由选择注入层级 → 综合回答
4. 引用溯源校验（复用现有 Source Verifier）
```

**关键设计**：Agent 只在需要时才编排，简单查询永远直走快路径。这样保证 90% 的查询毫秒级返回，只有复杂法律问题才付出 LLM 编排的成本。

### 5.5 第五阶段：Wiki 结构强化（知识资产化）

现有 wiki 形态已经很好，强化两点：

1. **知识条目加「争议点」元数据**：每条知识标注关联法条、关联案例、常见争议，让 Agent 检索时有结构化跳转路径。
2. **引用锚定到条款级**：利用 `.meta.json` + 语义切片的层级 ID，让最终答案的每个引用都能点回「哪份文件、哪一条、哪一款」——这是法律场景比通用 RAG 更硬的需求。

### 5.6 数据流总览（改良后）

```
                   ┌──────────────────────────────────────────┐
                   │              知识写入层                   │
                   │  人工撰写 .md + .meta.json               │
                   │  （wiki 结构，人可读，带版本/置信度）        │
                   └──────────────┬───────────────────────────┘
                                  ▼
                   ┌──────────────────────────────────────────┐
                   │              索引构建层                   │
                   │  语义切片（法律层级）→ 双路写入             │
                   │  ① embedding → PGVector/Qdrant           │
                   │  ② 分词/字段 → Elasticsearch              │
                   └──────────────┬───────────────────────────┘
                                  ▼
                   ┌──────────────────────────────────────────┐
                   │              查询编排层（Agent）            │
                   │  查询 → 快路径双路召回(RRF)                │
                   │  → 置信度不足时子查询拆解+外部法律库        │
                   └──────────────┬───────────────────────────┘
                                  ▼
                   ┌──────────────────────────────────────────┐
                   │              生成与校验层                  │
                   │  金字塔路由注入 → 模型生成                 │
                   │  → 引用溯源校验（逐条比对原文）             │
                   └──────────────────────────────────────────┘
```

## 六、落地优先级与工作量预估

| 阶段 | 内容 | 预估工作量 | 收益 |
|---|---|---|---|
| P0 | 加 embedding + 向量库，双路召回上线 | 3~5 天 | 语义召回 + 性能质变 |
| P1 | ES 倒排索引接入 | 2~3 天 | 精确检索 + 条款锚定 |
| P2 | RRF 融合排序 | 1 天 | 混合召回质量 |
| P3 | Agent 编排增强（子查询拆解） | 2~3 天 | 复杂问题多跳 |
| P4 | Wiki 争议点元数据 + 条款级引用 | 2~3 天 | 知识资产化 |

> **建议**：P0+P1 合为一个里程碑（约 1 周），先解决"1 万文件跑不动 + 语义召回缺失"两个最痛的点。P2~P4 后续迭代。

## 七、结论

1. **legalwork 现状**：Agentic 编排骨架 + wiki 结构化底座（约占理想形态的 60%），缺向量化与高性能索引。
2. **一万文件规模**：纯稀疏检索线性扫描不可行；纯向量 RAG 对法律场景精度不足；纯 Agentic Search 成本失控。
3. **最优解**：评论区说的「Agentic Search + wiki + 向量化」——即 **向量库（语义粗召）+ ES（精确匹配）+ Agent 编排（按需深度检索）+ 引用溯源校验** 的四层组合。
4. **legalwork 的改良路径**：保留现有 Agentic 编排资产，替换检索底层，分五阶段落地，P0+P1 一周内可解决最痛的性能与语义问题。
